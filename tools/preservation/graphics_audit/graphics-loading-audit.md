# Graphics loading script audit

Scope: 220 Ruby files under Scripts (202) and Plugins (18); archived tools packages excluded. Counts describe the final working-tree snapshot and exclude leading # comments plus Ruby =begin/=end comment blocks. These are lexical constructor call sites, not counts of runtime executions: 147 AnimatedBitmap, 277 Bitmap, 45 BitmapWrapper, plus the two internal PngAnimatedBitmap/GifBitmap factory calls. Of 322 raw Bitmap/BitmapWrapper constructors, 307 create procedural size-based canvases and 15 accept filenames (one shared-loader internal and14 external callers). Initial audit found15 external callers; choosing the boss bar once removed its redundant default-load call. See constructor-call-sites.tsv and raw-file-loads.tsv. Dynamic filename arguments remain classified as dynamic; a missing literal alone does not prove a live rendering failure.

## Shared-loader findings and central repair

- At the audit baseline, BitmapCache.open_bitmap only performed explicit filename resolution for Characters after native ENOENT. Other folders and raw constructors were unprotected against the same lookup failures. The central repair resolves filenames before native loading while preserving independent mutable bitmap ownership.
- At the audit baseline, SpriteWindow.rb pbResolveBitmap stripped only lowercase image extensions and only tried PNG/GIF. Explicit .PNG paths and BMP/JPG/JPEG could fail helper checks despite being native-supported. Use case-insensitive complete extension handling.
- At the audit baseline, GifBitmap swallowed every source loader error, made a transparent32x32 frame, and cached it under the requested source path (SpriteWindow.rb:608-646 in audit baseline). That hides corrupt/missing loads as invisible graphics; the legacy32x32 heuristic and filestring[0]==0x47 signature comparison also assume older Ruby semantics. Preserve deliberate nil/empty transparent frames separately from actual failed image loads, and avoid poisoning valid asset keys with fallback blanks.
- Implemented AzureBitmapFiles and one inherited Bitmap constructor hook. Every file-backed Bitmap/BitmapWrapper load resolves the actual basename and extension from a lazy directory index before native decoding. PNG, GIF, JPG, JPEG and BMP are supported, including mixed-case names. Directory modification times and BitmapCache.clear invalidate the index. Numeric canvas constructors and independent bitmap ownership retain their existing behavior.
- pbResolveBitmap uses the same resolver. Native Graphics.transition masks resolve after symbolic transition selection, preserving coded transitions. Unresolved names retain native/RTP/archive fallback. GifBitmap no longer caches missing-image placeholders as source images or rejects legitimate 32x32 images; existing files that cannot decode report the loading error.
- Public Cache and RPG::Cache helpers already funnel through BitmapCache; AnimatedBitmap, IconSprite, AnimatedPlane, ChangelingSprite, PokemonSprite and PokemonBattlerSprite also do. Their numerous call sites do not each need custom loaders.
- MakerStudio direct bitmap calls intentionally own full sheets or hue-modified fog images. Constructor resolution can cover them, but exchanging them for shared mutable cache references would introduce corruption and disposal bugs.
- No confirmed cache-source pixel mutation was found in live party/summary/Pokedex paths examined. Party panels and overlays draw into size-created BitmapWrapper/BitmapSprite canvases; PokemonUtilities clones before MultipleForms alterBitmap.

## Percy, battle backgrounds and regression coverage

- Map001 EV032 sets nextBattleBack to Dream before Percy. Native extensionless battlebgDream loading failed despite the supplied PNG; AnimatedBitmap hid that error behind a transparent 32x32 frame. The fixed full scene renders the supplied 512x288 Dream background, pixel CRC 1036464009, with both platforms visible.
- All 428 shipped Battlebacks PNGs were checked natively. Dream was the sole failing extensionless load in that directory; no wrong-image pixel mismatches were found. A separate literal scan identified 16 case mismatches across other graphics categories that the shared resolver covers.
- Battle art selection now applies field overrides before resolving terrain/time variants. Enemy and player bases independently fall back to supplied variants. Six old art names map to existing art: Burning to Volcano, Corrosive to Poison, Holy to Ruin, AmethystCave to CrystalCavern, and both field placeholders to GoldenArena. Field mechanics remain separate from those art aliases.
- Library consistently uses field ID 47. Each battle refreshes its stored restore artwork, preventing a previous battle's backdrop from being reused. Entry, restoration and mid-battle updates use the same resolution rules.
- Native checks passed 282 entry selections (47 fields, two override paths, three times), 144 restore/change selections, 18 uppercase alias combinations and 72 terrain/time combinations. Selected gameplay field IDs were checked alongside the graphics.
- The durable native fixture tools/preservation/engine_test/AzureBitmapLoadingFixture.rb passes 13 test groups: five image formats, filename case, prefix collisions, legitimate 32x32 images, raw/cached/UI callers, mutation and reference ownership, newly added files, missing/corrupt images, mocked archive fallback, transition delegation, cache clearing and reload safety. The clean pre-fix graphics scripts fail its first case.
- Native results are preserved in bitmap-loading-native.txt, battleback-fields-native.txt, battleback-final-native.txt and native-verification.txt alongside this report.
- Run that fixture as mkxp's customScript in an isolated game package outside this repository. Set AZURE_BITMAP_SOURCE to this repository and optionally AZURE_BITMAP_REPORT to the report path. Generated test images stay in the isolated working directory. Archive resolution is mocked in this fixture; normal native graphics and scene checks use the actual bundled Game.exe.
